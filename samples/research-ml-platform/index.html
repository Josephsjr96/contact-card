Research ML Platform

A production-style MLOps system for training, registering, canary-testing, promoting and automatically rolling back machine-translation models.

The problem

The research project compares NLLB-200 and M2M-100 on Persian ↔ German ↔ Polish poetic translation. New fine-tuned models must reach users safely, without anyone hand-editing production. This platform makes every model change a tracked, reversible event.

Model lifecycle

Train (LoRA)→Register→Canary 5%→Monitor→PromoteorAuto-rollback
Boundary rule. The Registry decides deployment state. Redis routes traffic. Inference serves but never decides. Prometheus observes. The rollback worker reacts. Nothing outside the Registry writes model or deployment state — enforced in services/registry/app/lifecycle.py.

What’s inside

  • Registry state machine — register, deploy-canary (percentage-controlled), promote, rollback, with one active candidate at a time and a full audit trail.
  • Deterministic traffic split — inference reads routing state from Redis, refreshed from the Registry in the background.
  • Automatic rollback — a worker queries Prometheus for the canary’s error rate over a rolling window and calls the Registry to roll back.
  • LoRA fine-tuning pipeline — trains NLLB with LoRA, logs to MLflow, uploads the adapter to MinIO and registers the version without touching production traffic.
  • Poetic-feature analysis — heuristic detectors per language surfaced in the dashboard.
  • Researcher tooling — human ratings, side-by-side NLLB-200 vs M2M-100 output, JSON / CSV export, discussion board.

Testing

Unit tests cover the lifecycle rules and the routing split. A golden integration test proves register → deploy → canary → promote and register → deploy → canary → rollback end-to-end against the real Registry app, no Docker needed.

Honest scope notes

  • No real parallel poetry corpus yet — training falls back to a tiny synthetic set so the pipeline is runnable end-to-end.
  • Rollback is error-rate based; a sampled quality metric (chrF++/COMET) is the planned second signal.
  • SQLite-first by design; each service isolates SQL so moving to PostgreSQL is a contained change.
  • No authentication / RBAC (explicit MVP non-goal).
